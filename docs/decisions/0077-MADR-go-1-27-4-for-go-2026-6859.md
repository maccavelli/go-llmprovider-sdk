# Require Go 1.27.4 for GO-2026-6859, Before Any of the Auth Series' Code

## Context and Problem Statement

`go.mod` says `go 1.27.3` (C1), set by
[0055-MADR-go-1-27-3-and-the-v1-20-0-release.md](0055-MADR-go-1-27-3-and-the-v1-20-0-release.md).
Both workflows install the version it names (C2, C3), and CI runs
govulncheck `v1.8.0` over the module (C4). Go 1.27.4 fixes an advisory in
`net/http` that govulncheck reports as called from this module when it is
built with Go 1.27.3.

Four records wait to change code here:
[0073-MADR-publish-an-auth-contract-module.md](0073-MADR-publish-an-auth-contract-module.md)
to
[0076-MADR-auth-error-kinds-and-doc-drift.md](0076-MADR-auth-error-kinds-and-doc-drift.md),
of which 0076 lands first. 0073-MADR D1 gives the nested module's `go` line
to "R54's floor as the root's `go.mod` states it when the module is
created", and says the floor rises only by a record of its own. This is
that record.

### The rules that apply

* **R54** of the standards guide: "The Go floor is `go 1.27.3`, with no
  `toolchain` line, and CI builds with the version `go.mod` names … The
  floor is raised with each Go security patch." (C5, C6; cited decisions
  0048-MADR D6 and A1, and 0055-MADR.)
* **0029-MADR** raised the floor from 1.27.1 to 1.27.2 for standard library
  findings, and rejected a `toolchain` line (C20), a pin in CI alone, and
  an exclusion. Its amendment says a toolchain move checks the linter pin
  too (C21). That raise shipped in the next minor release, `v1.4.0`,
  with the record that followed it (C22).
* **0055-MADR** raised it to 1.27.3 for GO-2026-6809 by the same option,
  and released it as a patch, `v1.20.1`, because `v1.20.0`'s tag run had
  failed on the finding and left the tag without a Release (C23).
* **R53:** every release has a changelog section (C7).

## Decision Drivers

* CI is red on the next code push and on the next weekly run until its Go
  has the fix (F2, F5).
* govulncheck reports the finding as called, through servers this module
  starts (F4).
* R54 asks for the raise, and two records set the pattern.
* The auth series starts changing code with 0076. Its first code phase
  should begin on a gate that passes, and a red run should not be read as
  that phase's doing.
* A raised floor is a requirement imposed on every consumer.
* The sibling repositories are split three ways (F7 to F9), so no single
  line here matches them all.

## Considered Options

* **A. Raise `go.mod`'s `go` line to `go 1.27.4`,** now, in a change of its
  own, before any of 0076's code.
* **B. Keep `go 1.27.3` and add `toolchain go1.27.4`,** as acp-go-sdk2 does
  (F8).
* **C. Do nothing until 0076,** and raise the floor with its first code
  phase.

Two more were rejected by 0029-MADR and again by 0055-MADR, and are not
reopened: pinning CI's `setup-go` alone, and excluding the finding from
govulncheck (each record's "Pros and Cons of the Options").

## Decision Outcome

Chosen option: "A. Raise `go.mod`'s `go` line to `go 1.27.4`", because it is
the one option where `go.mod`, CI and every consumer's minimum agree on a
standard library with the fix, as 0029-MADR and 0055-MADR found, because
R54 says so, and because a change of its own keeps the floor apart from the
auth series' first code. The owner approved it on 2026-11-11, to land before
any of 0076's code.

### D1. The floor is `go 1.27.4`

* `go mod edit -go=1.27.4`: one line, no `toolchain` line, `go.sum`
  unchanged, `go mod tidy -diff` clean.
* **The linter.** 0029-MADR's amendment says a toolchain move checks the
  linter pin (C21). golangci-lint `v2.14.0` is run under Go 1.27.4 before
  the change is staged. A patch release is not expected to change the
  export data format **[assumption, measured by the PLAN]**. If it fails,
  the PLAN stops.

### D2. Where the floor is stated

* **R54** reads "`go 1.27.4`" and names GO-2026-6859 (`net/http`) as the
  patch's reason, keeping its rule that the floor rises with each Go
  security patch. Its row in the guide's index cites this record beside
  0048-MADR A1 and 0055-MADR. That is the amendment of R54's cited decisions
  that AGENTS.md's "API work" asks for: 0048-MADR gains its next amendment
  (A6, at `773b84c`), a pointer here, and 0055-MADR an amendment saying its
  floor is raised again.
* **The current-state statements say 1.27.4:** `AGENTS.md`, the README
  (twice), `docs/architecture.md` and the migration guide. The PLAN lists
  each line.
* **Left as they are:** records, which say what ran then; `CHANGELOG.md`'s
  `v1.20.1` section, which is that release's; and
  `scripts/test_gates.py`'s scratch module, whose `go 1.27.1` states nothing
  about this module (0055-MADR D1 left it for the same reason).

### D3. It lands before 0076's code, with no release of its own

* **One commit on `main`,** before the first phase of
  [0076-PLAN-auth-error-kinds-and-doc-drift.md](0076-PLAN-auth-error-kinds-and-doc-drift.md)
  that changes code. The other three PLANs of the series follow 0076, so
  the floor is in place for all four.
* **`CHANGELOG.md`'s `[Unreleased]` gains a Security entry,** which names
  GO-2026-6859 and what a consumer must do. It ships in the next release,
  `v1.30.0`, which 0076 carries.
* **No tag for the floor alone.** Neither R53 nor R54 asks for one. Of the
  two earlier raises, 0029's shipped in the next minor with the record that
  followed it (C22), as this one does. 0055's patch release answered a tag
  whose CI had failed and which had no Release (C23); `v1.29.0`'s tag run
  passed and it has its Release (F5). A consumer's safety is decided by the
  toolchain it builds with, not by this module's directive (0029-MADR's
  Context), and `v1.29.0` builds with Go 1.27.4 as it is.
* **The nested module follows.** `authcontract/go.mod` takes this floor when
  0073-PLAN's Phase 1a creates it (0073-MADR D1).

### D4. Observed, not decided: `golang.org/x/term` and `golang.org/x/sys`

`golang.org/x/term` is at `v0.43.0`, with `v0.48.0` available, and
`golang.org/x/sys` at `v0.47.0`, with `v0.50.0` available (F10; C14, C15).
govulncheck reports nothing in either. This record changes neither: a move
of a requirement is its own change, with its own reason.

### Consequences

* Good, because CI's govulncheck step passes with no exclusion, and CI and
  this host run the same toolchain again.
* Good, because a consumer that runs `go get` on the next release gets
  `go 1.27.4`. With `GOTOOLCHAIN=auto`, the default, its `go` command then
  selects a toolchain with the fix.
* Good, because 0076's first code phase starts on a passing gate, and the
  commit that raises the floor holds nothing else.
* Bad, because a consumer at `go 1.27.3` must raise its own directive to
  take `v1.30.0`. gobble-cli is one (F9), though its own CI already needs
  the raise. One built with `GOTOOLCHAIN=local` on 1.27.3 cannot build it.
* Bad, because between this commit and `v1.30.0` no tag carries the floor:
  a consumer learns of it from `[Unreleased]`, or from its own govulncheck.
* Neutral, because magic-cli-remote is already at `go 1.27.4` (F7), and
  acp-go-sdk2, which keeps a lower floor behind a `toolchain` line (F8),
  does not import this module.
* Neutral, because `go.sum` and the requirements do not change (D4).

## Pros and Cons of the Options

### A. Raise `go.mod`'s `go` line to `go 1.27.4`

* Good, because one line sets CI's Go, the module's minimum and its
  consumers'.
* Good, because it is R54's rule, applied as 0029-MADR and 0055-MADR
  applied it.
* Good, because magic-cli-remote made the same move for the same advisory
  (F7), so the two modules that share a build agree.
* Neutral, because `go.sum` and the requirements do not change.
* Bad, because every consumer must be at 1.27.4 to take the next release.

### B. Keep `go 1.27.3` and add `toolchain go1.27.4`

* Good, because consumers' minimum stays 1.27.3: nothing is imposed on
  gobble-cli.
* Good, because a sibling does it: acp-go-sdk2 keeps a `go 1.26.11` floor
  and builds itself with 1.27.4 (F8).
* Neutral, because what that gives acp-go-sdk2, a floor a whole minor
  version below its toolchain, is not to be had here: this module needs Go
  1.27 (0048-MADR A1), so both lines would name a 1.27 patch, and the lower
  one would keep only a patch that lacks the fix.
* Bad, because a `toolchain` line in a dependency is ignored by consumers
  (C20), so it protects only this repository's own builds, and consumers
  get no signal that 1.27.3 lacks the fix.
* Bad, because R54 says "with no `toolchain` line" (C5): the rule and its
  cited decisions would have to change first.
* Bad, because CI's Go would rest on how `setup-go`'s `go-version-file`
  treats a `toolchain` line, which 0029-MADR did not check for the pinned
  `v7.0.0`, and which is not checked here either.

### C. Do nothing until 0076

* Good, because it needs no record and no commit of its own, and the floor
  moves with code that ships.
* Bad, because 0076's first code phase could not pass CI until the floor
  rose, so the raise would be folded into a phase about error kinds, and a
  red run there would have two possible causes.
* Bad, because 0076-MADR is `proposed`: the floor would wait on its
  acceptance, while the weekly run on `main` fails from 2026-11-16
  **[inferred from F2]**.
* Bad, because R54 raises the floor with each Go security patch, not with
  the next feature.
