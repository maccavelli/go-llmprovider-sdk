# Implement the Cache-Write Counts in `Usage`

Associated MADR: [0036-MADR-cache-write-token-count.md](0036-MADR-cache-write-token-count.md)

## Goal

When it is done:

* `llmprovider.Usage` has `CacheWriteTokens` and `CacheWrite1hTokens`
  (0036-MADR D1), each a part of the count before it:
  `CachedTokens + CacheWriteTokens <= InputTokens`, and
  `CacheWrite1hTokens <= CacheWriteTokens`.
* Each wire decodes them as D2 gives:
  * Messages from `cache_creation_input_tokens` and
    `cache_creation.ephemeral_1h_input_tokens`, in a body and in a stream;
  * Responses from `input_tokens_details.cache_write_tokens`;
  * Chat Completions from `prompt_tokens_details.cache_write_tokens`;
  * generateContent and Interactions leave both at zero.
* `api-standards.md` R7 and `llmtest`'s R7 check hold the new rules (D3).
* Every canned reply that can report a write reports one, and each
  provider's decoded `Usage` is checked against it.
* A live measurement, run before the decoders change, shows what each
  service sends. A second run, after the change, shows the decoded counts
  match it.
* `v1.10.0` is released, and only grows the API: two fields.

No existing count changes meaning. No request changes: nothing here asks a
service to cache (D4).

## Scope

### In scope

* **The type:** `llmprovider/contract.go` (`Usage`).
* **The decoders:**
  * `llmprovider/internal/wire/messages/messages.go`: `usage`,
    `usage.counts`, and the stream's merge in `Events`;
  * `llmprovider/internal/wire/responses/responses.go`: `usage`;
  * `llmprovider/internal/wire/chatcompletions/chatcompletions.go`: `usage`.
* **The checks:**
  * `llmprovider/llmtest/llmtest.go` (`checkResponse`'s R7 block) and
    `llmtest_test.go`;
  * `llmprovider/internal/wirecase/wirecase.go`: the canned replies, the
    expected `Usage` values and `usageFor`.
* **Tests:**
  * `usage_test.go` in `messages`, `responses`, `chatcompletions`,
    `generatecontent` and `providers/gemini`;
  * a new live measurement, `llmprovider/live_0036_cache_write_measure_test.go`.
* **Docs:**
  * `docs/guides/api-standards.md` R7;
  * `docs/architecture.md`, the `Response.Usage` paragraph;
  * `README.md` Status, and this PLAN's release notes;
  * `docs/README.md`'s index.

### Out of scope

As 0036-MADR D4 decides:

* any request field that asks for caching: `cache_control`,
  `prompt_cache_retention`, `prompt_cache_options`;
* a cost helper, and a 1-hour price in `ModelRates`;
* gobble-cli's adapter, and its double count of cache reads, which belong
  to that repository;
* `docs/guides/migrating-from-mcplib.md`: `Usage` has no `mcplib`
  ancestor, so it gains no row.

## Rules for every phase

* **Red first.** Each new assertion is seen failing before the change that
  makes it pass, and its FAIL lines are recorded.
* **Plants** go through `tools/plant.py`, on a scratch clone, never in the
  tree. Each plant's FAIL lines are recorded.
* **Every script is Python,** and a script worth running twice goes in
  `tools/` (0035-MADR).
* **A phase is staged only after:**
  * `make pre-add-check FILES="…"` on its Go files;
  * `make records-check`;
  * `tools/denyscan.py --changed` and `tools/linkcheck.py`;
  * the gate, `tools/gate.py`, at 23 of 23.
* **Billed requests:** the count is given to the owner, and the owner
  approves, before any live run.
* **Keys** are read only from the environment by the live tests, and are
  checked for presence only. None is printed or recorded.
* **A deviation stops the work:** evidence, options with the recommended
  one first, and a dated entry here, plus a MADR amendment where a fact or
  a decision changes.
* **The owner commits** each phase. Pushing and tagging are the owner's.

### Phase 1: measure what each service sends

Nothing in the module changes. The test records what the decoders will
read, before they read it.

1. **`llmprovider/live_0036_cache_write_measure_test.go`**
   (`//go:build live_gateways`, package `llmprovider_test`):
   * **`TestLive_0036CacheWrites`.** It is skipped unless
     `LLMPROVIDER_LIVE_0036` is set, and each target is skipped unless its
     key variable (`ProviderEnvVars()`) is set.
   * **The request:** a fixed prompt of about 6,000 tokens in
     `Instructions`, the same on both requests. It is numbered lines of
     plain text, generated by the test. One short user turn follows, with
     `WithMaxTokens(16)`. The prompt clears every service's caching
     minimum: OpenAI's 1,024 tokens, and Anthropic's per-model minimums.
   * **Two identical `Generate` calls per target,** a few seconds apart. The
     first may write the cache, and the second may read it.
   * **A recording transport,** like `live_usage_test.go`'s
     `replyRecorder`, keeps each response body. The test logs only the
     body's `usage` (or `usageMetadata`) object, re-encoded on one line,
     and the decoded `Usage`. It logs no prompt, header or key.
   * **It asserts only what the MADR already states as fact:**
     * every count in the raw usage is zero or more;
     * when a body has both a read and a write count, their sum is no
       larger than the input total in that wire's convention. On Messages
       the input total is `input_tokens + cache_read_input_tokens +
       cache_creation_input_tokens`; elsewhere it is the reported input
       count;
     * on Messages, when `cache_creation` is present, its two counts sum
       to `cache_creation_input_tokens`.
2. **The targets:** eight, so sixteen billed requests.

   | # | Provider | Model, picked at run time | Wire | Expected, from 0036-MADR |
   | :--- | :--- | :--- | :--- | :--- |

   | T2 | claude | `claude-haiku-5-5` | Messages | no write: the request carries no `cache_control` |
   | T3 | grok | `grok-4.6` | Responses | no write field: xAI documents none |
   | T4 | kilo | an OpenAI GPT-5.6-or-later model the live model picker finds active in Kilo's section (`openai/gpt-6-luna` first) | Chat Completions | `cache_write_tokens` present; a write unmeasured |

   | T6 | opencode-zen | a `claude-` model the picker finds active (`claude-haiku-5-5`, then `claude-sonnet-5-5`) | Messages | unmeasured: whether Zen passes Anthropic's counts through |
   | T7 | opencode-zen | `gpt-6-luna`, then `gpt-6.1-sol` | Responses | unmeasured |
   | T8 | opencode-zen | `deepseek-v4.1-flash` | Chat Completions | no write field: DeepSeek reports none |

   A model the picker cannot find skips that target, with its reason.

### Phase 2: the type, the rule and its check

1. **Red first** (`llmprovider/llmtest/llmtest_test.go`, the table of bad
   responses). Three new rows:

   | Row | `Usage` | Want |
   | :--- | :--- | :--- |
   | `negative cache write` | `{InputTokens: 5, CacheWriteTokens: -1}` | `negative usage` |
   | `cache read and write beyond input` | `{InputTokens: 5, CachedTokens: 3, CacheWriteTokens: 3}` | `a part larger than its total` |
   | `1-hour writes beyond writes` | `{InputTokens: 5, CacheWriteTokens: 2, CacheWrite1hTokens: 3}` | `a part larger than its total` |

   They fail first to compile, since the fields do not exist. Then, with
   only the fields added, they fail on their want: no failure is reported.
2. **Change:**
   * **`llmprovider/contract.go`:** the two fields, with D1's comments. The
     type's comment gains the rule: a total holds its parts, and
     `CachedTokens` and `CacheWriteTokens` do not overlap.
   * **`llmprovider/llmtest/llmtest.go`:** the negative check covers both
     fields. The part check becomes `u.CachedTokens + u.CacheWriteTokens >
     u.InputTokens || u.CacheWrite1hTokens > u.CacheWriteTokens ||
     u.ReasoningTokens > u.OutputTokens`.
   * **`docs/guides/api-standards.md` R7:** D3's sentence, citing 0036-MADR.
3. **Plants:**
   * the part check without `CacheWriteTokens`;
   * the part check without the 1-hour rule;
   * the negative check without `CacheWriteTokens`.

   Each must fail its row.
4. **Green:** `go test ./llmprovider/llmtest/`, then every provider's
   `llmtest.Run`, unchanged, since every decoder still reports zero writes.
5. Gate; stage. The owner commits.

## Rollout and Rollback

* **Rollout:** the records, then one commit per phase, then `v1.10.0`.
  Phase 1 changes no module code. Phase 2 adds the fields, which stay zero
  until Phase 3. Each commit keeps every check green.
* **Compatibility:** two exported fields are added to a struct. apidiff,
  which `make api-check` runs against the latest v1 tag (R48), reports an
  added field as compatible. A caller that writes a `Usage` literal without
  field names would no longer compile. No such literal exists in this
  repository. A caller comparing a whole `Usage` sees new values only where
  a service reports writes.
* **Rollback:** Phase 3 reverts alone, and the fields read zero again.
  Phase 2 reverts with Phase 3 before a release. After `v1.10.0`, a field
  cannot be removed in v1 (R48), so a fault is fixed forward in a patch
  release.
